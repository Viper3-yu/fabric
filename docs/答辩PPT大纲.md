# 答辩 PPT 大纲与讲稿

答辩时间 10 分钟：**7 分钟展示 + 3 分钟提问**。本大纲按 10 页设计，每页标注了建议用时和口播要点，全部讲完约 6 分 30 秒，留出缓冲。

## 制作原则

- 沿用项目视觉：森林绿强调色 + 纸白背景，标题可用项目同款衬线体，交易 ID 用等宽字体。
- 一页只讲一件事，字少图多；系统截图直接从运行中的页面截取，别用示意图替代真实界面。
- 涉及"链上证据"的页面放真实交易 ID 截图，这是最有说服力的素材。

## 第 1 页：封面（10 秒）

- 内容：项目名「迹信 —— 基于 Hyperledger Fabric 的可信物流追踪系统」、组号、成员姓名。
- 口播："我们是 X 组，作品叫迹信，一套基于 Hyperledger Fabric 的可信物流追踪系统。"

## 第 2 页：要解决什么问题（40 秒）

- 内容：三方物流的三个痛点，各配一句说明——
  1. 轨迹由单一平台维护，可被单方修改；
  2. 交接责任难界定，出纠纷各说各话；
  3. 温控货物异常证据分散，收货结果形不成可信闭环。
- 口播：用一个具体场景带入（例如"一批疫苗运输到目的地温度超标，发货方说是承运方的问题，承运方说是收货方开箱不当，谁也拿不出证据"）。

## 第 3 页：产品方案（40 秒）

- 内容：四角色闭环流程图（建单 → 接单 → 揽收 → 节点/异常 → 送达 → 签收），标注每个动作由哪个角色完成。
- 口播："每个关键交接都是一笔真实的 Fabric 交易——谁在什么时间做了什么，链上有据可查，任何一方无法事后单独篡改。"

## 第 4 页：技术架构（50 秒）

- 内容：三层架构图——React + TypeScript 浏览器端 → Go 标准库 HTTP API（JWT 鉴权、严格校验）→ Fabric Gateway SDK → 双组织 Peer（Org1MSP / Org2MSP）+ Go 链码 + CouchDB。
- 口播要点：**"API 没有自己的业务数据库，页面看到的所有状态都来自账本"**——这句是区分"真链上应用"和"套壳演示"的关键。

## 第 5 页：区块链用在哪里（60 秒，全片核心）

- 内容：五行列出链码职责——
  1. 状态机强制流转：不能跳过揽收直接签收、不能重复签收；
  2. 组织即权限：链码校验调用者 MSP，伪造前端请求也无法越权；
  3. 可信时间与责任链：事件带提交者 MSP、交易 ID、Fabric 交易时间；
  4. 签收码与凭证只存 SHA-256 摘要，明文不上链；
  5. 温度越界由链码自动判定并记录异常，异常记录不可删除。
- 口播：逐条讲，每条一句话。这一页回答"为什么必须是区块链"。

## 第 6 页：功能演示（60 秒）

- 内容：四宫格真实截图——创建运单（含签收码提示）、承运方节点录入与异常、公开查询脱敏轨迹与交易证据、记录核对结果。
- 口播：配合PPT 简述，或直接切现场演示/播放演示视频中的关键片段。"每一步操作的响应里都返回真实交易 ID。"

## 第 7 页：创新点——控制塔与双组织交接（50 秒）

- 内容：统一链码统一账本示意 + 双边交接时序（Org1 `InitiateHandover` → Org2 `ConfirmHandover`，两笔独立交易）；控制塔页面截图（路线、节点、温度曲线）。
- 口播：强调三点——控制塔与运单业务共用一条链码（不是两套系统）；发起方无法自确认，重复确认被链码拒绝；包裹/物流单元装箱关系上链存证。

## 第 8 页：工程质量（40 秒）

- 内容：测试与工程化清单——
  - 前端 26 项组件测试 + Vitest；Go 单元与 API 闭环测试（文件型测试替身，不需 Docker）；
  - `pnpm test:fabric` 在真实测试网络跑通建单到签收闭环；
  - GitHub Actions CI 全绿（类型检查、lint、构建、测试）；
  - 安全：bcrypt 密码哈希、httpOnly JWT cookie、公开接口限流、隐私脱敏；
  - 文档：README、设计方案、操作手册、Ubuntu 部署指南、审计记录。

## 第 9 页：总结与展望（30 秒）

- 内容：完成度对照（功能完整、真实上链、自动化验证）+ 后期改进（Fabric 私有数据集合、对接真实 IoT 温度设备并校验设备证书、链码事件接入消息队列通知、多 orderer 与高可用 CA 的生产拓扑）。
- 口播："对照课程要求逐项达成；生产化路线已经明确，见部署文档。"

## 第 10 页：团队分工（20 秒）

- 内容：成员分工与贡献值表（与项目介绍文档一致）。
- 口播：一句话带过每人负责的模块，致谢结束。

## 3 分钟提问：高频问题与答法

| 可能的问题                     | 回答要点                                                                                                                      |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| 为什么用 Fabric 而不是以太坊？ | 联盟链贴合多方物流协作：已知参与组织、需要 MSP 级权限与吞吐、无需代币激励；以太坊公链的 Gas 与匿名参与方不符合场景            |
| 隐私怎么保护？                 | 链上只存脱敏字段与 SHA-256 摘要，原文与完整联系方式留在业务方；公开查询只返回脱敏视图；后续可用私有数据集合进一步隔离         |
| 怎么证明不是模拟数据？         | 页面展示账本模式与真实交易 ID，可用 CouchDB/链码查询核对；`test:fabric` 在真实网络跑闭环；API 不设业务数据库                  |
| 性能如何？                     | 测试网络面向教学，未做压测；架构上写路径经双组织背书，读路径可扩展多 Peer 负载均衡，这是 Fabric 常规扩展方式                  |
| 测试用替身算真实上链吗？       | 不混淆：替身只用于无 Docker 环境的单元/闭环测试，页面业务请求全部走真实 Fabric Gateway，响应带真实交易 ID                     |
| 和生产环境的差距？             | 当前为官方测试网络 + cryptogen 证书；生产需各组织独立节点与 CA 签发证书、TLS、多 orderer 高可用，对照 `deploy/README.md` 清单 |
